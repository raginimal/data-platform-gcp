02 — Architecture baseline

Lock the boundaries, not every decision

The project's approved architecture is recorded once, in docs/architecture/baseline.yaml. It complements policy: policy says what must be true, the baseline says what this project approved.

LOCKED — APPROVED BASELINE

  • Application pattern and layering
  • Components and service contracts
  • Platform and infrastructure provider
  • Data platform, stores, and contracts
  • AI integration pattern and model provider / family
  • Identity model and trust boundaries
  • Deployment topology, environments, and CI/CD gates

FLEXIBLE — DEVELOPER DECISIONS

  • Feature code and module internals
  • Schemas and queries inside an approved store
  • Libraries inside the approved platform
  • Prompt wording and evaluation data
  • Model version inside the approved family
  • Individual least-privilege grants
  • Resource sizing inside the approved topology
The Golden Path provides a stable architectural boundary. Developers innovate inside that boundary. Meaningful deviations are detected and deliberately reviewed. The baseline ships as draft and is enforced once the architecture owner sets status: approved.
03 — Architecture baseline guard

Detect first, then review

The guard is a deterministic script, scripts/validate-baseline.sh, run by the Policy workflow on pull requests. It classifies the change; agents and humans judge it.

NO_BASELINE_IMPACT

Normal PR workflow. No ADR needed.

BASELINE_IMPACT

Relevant agent and owner review. The guard does not fail CI.

05 — Core contract

Policy → Skill → Agent → Workflow → Human

The relationship is explicit: what, how, which, when, and who. The architecture baseline sets the project's approved boundary these are applied to; it does not replace policy.

Baseline — BOUNDARY

Defines the project's approved architectural boundaries (docs/architecture/baseline.yaml). Complements policy; does not replace it.

Policy — WHAT

Defines what must be true, with stable IDs, normative language, exceptions, and automation candidates.

Skill — HOW

Defines how a focused check is performed, including evidence, severity, confidence, and false positives.

Agent — WHICH

Selects relevant skills and provides contextual reasoning. It is advisory and read-only by default.

Workflow — WHEN

Supplies changed files, PR context, policies, CI results, and the point in the lifecycle.

Human — WHO

Makes accountable decisions for risk, exceptions, IAM, architecture, security, data, AI, merge, and production.

SEC-001 example → Secret Review Skill → Security & DevOps Agent → Pull Request → Human escalation if required.

07 — Agent layer

Four custom agents

Click an agent to reveal its actual skill set and escalation boundary. The Baseline Guard routes to these four agents; it is not a fifth agent.

ARCH-AGENT-001

Architecture Agent

Architecture, dependencies, APIs, data contracts, ADRs, and trade-offs.

  • Architecture Review
  • Dependency Analysis
  • ADR Review
Receives baseline-impacting changes from the Baseline Guard and recommends whether an ADR is needed. Escalates material boundaries and architecture decisions to humans; cannot approve them or edit the baseline.
SEC-DEVOPS-AGENT-001

Security & DevOps Agent

Security, IAM, secrets, CI/CD, IaC, and operational risk.

  • Secret / IAM / Dependency Review
  • CI / CD / IaC Review
Assesses IAM, infrastructure, and deployment impact of baseline-impacting changes. Cannot access production credentials, change IAM, approve deployment, or override controls.
AI-AGENT-001

AI Engineering Agent

Models, prompts, RAG, embeddings, evaluations, guardrails, and AI security.

  • Model Review
  • Prompt Review
  • Evaluation Review
Assesses AI integration and model-boundary impact of baseline-impacting changes. Escalates consequential, unsafe, sensitive, or irreversible AI behavior.
QUAL-AGENT-001

Code Quality Agent

Maintainability, tests, complexity, duplication, errors, and documentation.

  • Code Review
  • Test Review
Does not replace deterministic formatting, linting, or tests.

09 — Enforcement boundary

CI versus AI agents

Deterministic controls remain authoritative.

DETERMINISTIC CI

  • Formatting and linting
  • Tests
  • Secret scanning
  • SAST and dependency checks when configured
  • IaC and container checks when assets exist
  • Policy and repository validation
  • Baseline file validation and change detection (Baseline Guard)
  • ADR metadata check once the baseline is approved

AGENTS (ADVISORY)

  • Contextual reasoning and trade-offs
  • Architecture impact
  • Security and IAM implications
  • AI architecture implications
  • Code quality reasoning
  • Recommendations, never approvals

HUMAN

  • Final architecture decision
  • Baseline approval and change
  • Exception approval
  • Merge and production approval
If it can be reliably checked deterministically, prefer CI. Use AI agents where contextual reasoning adds value.

13 — Principles

Engineering principles

Concise expressions of the repository's policy model.

Secure by default

Security starts at repository creation.

Policy driven

Intent is explicit and versioned.

Deterministic before AI

Reliable rules belong in CI.

Human accountable

High-risk decisions remain human.

Least privilege

Access is bounded by purpose.

Technology neutral

Overlays add platform specifics.

Reusable

Teams start from the same foundation.

Traceable

Changes and approvals connect.

Fail safely

Uncertainty escalates.

Boundaries, not decisions

Lock architecture and engineering boundaries, not every developer decision.

No version sprawl

No per-prompt, model, context, agent, or skill version governance.

Simple over platform

Prefer simple architecture to platform complexity.
